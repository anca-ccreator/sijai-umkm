# Panduan pengembangan SIJAI UMKM

## Status dan bahasa kerja

**Acuan pelaksanaan terkini:** pemilik memberi izin coding lokal menyeluruh untuk menyelesaikan **MVP SIJAI UMKM** dengan data sintetis. Fondasi G1-A sampai B3.4 dipertahankan tanpa rewrite. Selesaikan registri, verifikasi field, koreksi K1–K4, profil pangan, dashboard/monitoring, administrasi dan antarmuka end-to-end secara bertahap tetapi berkesinambungan; jangan meminta izin per modul. Kontrak dan keputusan KB/DT tetap menjadi batas. E1/ekspor, data nyata, PDN/cPanel/produksi/deployment, integrasi eksternal, marketplace/pembayaran/program bantuan, penetapan OPD/petugas nyata dan audit eksternal tetap tertutup. QA browser memakai akun sintetis dan bukti nyata. Satu ZIP/penyerahan komprehensif dibuat saat MVP siap demonstrasi, bukan setiap perubahan kecil.

- C2 hanya paket minimum induk, melalui SessionRegistryGateway dan RegistrationService B2 yang dipertahankan. Aktor/mandat/OPD/tujuan/waktu dari server; pembuat registrasi maupun Unit tidak boleh mengesahkan buatannya sendiri meski beberapa peran/admin. APPROVE_INITIAL diperiksa lagi setelah evaluasi paket, beserta lingkup dan masa. D1/M1 tidak memberi superuser.
- Gunakan katalog C2 sintetis berversi/efektif terpisah dari persetujuan pengajuan. Kosong/tidak sah/ambigu menghasilkan UNKNOWN, bukan lulus. A3/B1/kandidat dinilai ulang; NIB opsional. C2 tidak mengubah field DRAFT_UNVERIFIED atau sektor NOT_STARTED. Revisi lama bukan bukti versi baru.
- INITIAL_APPROVED/INITIAL_REJECTED final pada subset lokal ini; RETURNED menuju NEEDS_CORRECTION. Tidak membuka kembali/mengoreksi keputusan final atau nilai resmi dari izin ini. Versi/request/sidik katalog dan transaksi keputusan/bukti/riwayat/otorisasi/audit/outbox wajib; audit gagal berarti rollback/hasil ditahan. Halaman C2 tidak mengirim ID/isi/checksum dokumen atau ID mandat ke browser.
- Sepuluh migrasi: sembilan lama utuh + 010 tiga tabel C2 append-only. Dev hanya maju; fresh/rollback hanya test. Hak runtime C2 hanya SELECT/INSERT pada tiga tabel baru. Tanpa paket baru. Jalankan satu suite/QA per database test; dua proses bersamaan hanya kasus konkurensi terkelola dalam suite.
- Pertahankan A3, NIB opsional, M:N, cabang, revisi dan audit B2. D1 tetap katalog organisasi INTERNAL pada subset lokal, M1 mempertahankan scope asal; admin atau gabungan peran tidak menjadi pengesah/superuser atau melewati larangan pembuat sahkan induknya sendiri. Field yang ditolak tidak boleh bocor melalui HTML/JSON/atribut tersembunyi.
- Tidak ada paket baru B3.3; gunakan sepuluh migrasi dan MySQL khusus B1/B2 dengan tambahan C2 yang disetujui. Fresh/rollback hanya test. Sesi file terenkripsi/JSON, cookie HttpOnly/Strict/host-only, tanpa remember-me; batas waktu/percobaan lokal bukan SOP resmi. Demo CLI B3.1/B3.2 dipertahankan. Demo C2 eksplisit menolak menimpa atau meningkatkan hak akun/demo lama; hanya data/hak fiktif; tanpa kata sandi bawaan atau mencetak rahasia.
- Audit login/penolakan/baca/mutasi terkait/outbox wajib; gagal audit menahan hasil atau rollback SQL. Logout tetap memusnahkan sesi walau audit terganggu dan melaporkan gangguan. Salinan audit independen hanya rancangan, tanpa worker/koneksi baru. Jangan mengakses server/Excel historis/OSS/Dukcapil, menetapkan OPD/mandat nyata, memasang paket atau deployment. ZIP perubahan sumber/dokumen dengan manifest tetap wajib.

## Audit dua lapisan KB-12

- Model B menetapkan audit operasional di database aplikasi dan salinan dengan kontrol keamanan/administratif serta kewenangan terpisah. Dua tabel/lokasi dengan administrator dan kontrol sama tidak memenuhi pemisahan. Salinan bukan SSOT UMKM kedua.

- Letakkan aturan bisnis dalam layanan aplikasi yang dipakai semua jalur penulisan. Komponen Livewire menangani interaksi, bukan menjadi satu-satunya tempat aturan bisnis.
- Periksa akses di server untuk setiap aksi, objek, field, dan cakupan data. Tombol tersembunyi, ID dari browser, status komponen, serta hubungan kepemilikan bisnis saja bukan bukti izin.
- Pakai daftar field yang boleh diubah; jangan menerima nama tabel, nama kolom, atau identitas OPD dari browser sebagai sumber kewenangan.
- Tolak perubahan yang memakai versi data lama; jangan menimpa perubahan pengguna lain secara diam-diam. Persetujuan berulang tidak boleh menerapkan perubahan dua kali.
- Usulkan skema relasional dengan foreign key, batas keunikan yang terukur, transaksi InnoDB, dan kolom bertipe jelas. Metadata field mengatur kewenangan, bukan alasan menyimpan seluruh master dalam tabel nilai bebas.
- Hak akses dan audit berlaku juga pada pembacaan data sensitif, unduhan, pencarian, dan ekspor yang kelak disetujui. Terapkan minimisasi dan penyamaran data.
- Simpan lampiran sensitif secara privat. Catatan audit dibatasi aksesnya dan tidak memuat password atau token. Audit di database aplikasi saja belum menjamin kebal terhadap pengelola database.

## Paket ZIP untuk setiap perubahan arsitektur

Aturan tetap ini ditetapkan pengguna pada **5 November 2026** dan berlaku tanpa menunggu permintaan ZIP terpisah.

1. Setiap selesai melakukan perubahan arsitektur atau dokumen fondasinya, termasuk keputusan bisnis, model data, kamus data, kewenangan dan roadmap yang terkait, buat **satu ZIP berisi seluruh file baru atau yang diperbarui dalam rangkaian perubahan tersebut**. Sertakan versi terbaru AGENTS.md dan indeks bila ikut berubah. Pada tahap perencanaan, isinya hanya dokumentasi yang diizinkan.
2. Pertahankan struktur folder relatif terhadap akar proyek, misalnya AGENTS.md pada akar dan dokumen di docs/. Gunakan daftar file yang jelas; jangan memasukkan seluruh folder tanpa memeriksa isinya.
3. Gunakan nama ZIP yang menjelaskan topik, tanggal, dan revisi bila diperlukan. Simpan di akar proyek; jangan menimpa arsip lama atau memasukkan ZIP lama ke ZIP baru. Jangan sertakan rahasia, data pribadi nyata, dump produksi, dependensi unduhan, atau metadata Git.
4. Buat paket setelah seluruh perubahan dan pemeriksaan dokumen selesai. Pastikan jumlah/daftar entri sesuai dan bandingkan sidik SHA-256 setiap entri dengan file sumber. Jika sumber berubah sesudah pengemasan, buat ulang paket yang sesuai sebelum menyerahkan hasil.
5. Jika ada file dipindah, diganti nama atau dihapus, catat tindakan tersebut secara jelas dalam ringkasan atau daftar perubahan; ZIP sendiri tidak menjelaskan penghapusan file lama.
6. Pada jawaban akhir, berikan tautan unduh ZIP, jumlah file dan hasil pemeriksaan isi. Nyatakan bahwa paket memuat file baru/yang berubah pada rangkaian pekerjaan itu. Pembuatan ZIP tidak memberikan izin instalasi, implementasi aplikasi, perubahan database atau hosting.

## Cara menyelesaikan pekerjaan

1. Pastikan tahap dan ruang lingkup yang diizinkan, baca dokumen, dan periksa file yang sudah ada.
2. Bedakan fakta terverifikasi, keputusan pengguna, rekomendasi teknis, dan keputusan bisnis yang belum final. Rujuk nomor keputusan `KB-xx` bila relevan.
3. Kerjakan bagian yang sudah diizinkan. Bila ada keputusan bisnis yang memengaruhi hasil, ajukan pertanyaan terarah dan lanjutkan pekerjaan independen yang aman.
4. Pada implementasi kelak, jalankan pemeriksaan yang sesuai perubahan. Untuk kewenangan dan integritas data, uji penolakan lintas OPD, manipulasi ID, pencabutan izin, usulan kedaluwarsa, persetujuan serentak, dan kegagalan audit. Jangan mengklaim tes lulus bila belum dijalankan.
5. Perbarui dokumen jika desain berubah. Catat keputusan baru, pihak yang menyetujui, tanggal, alasan, dan dampaknya. Jangan mengubah status keputusan terbuka menjadi disepakati tanpa konfirmasi pengguna.
6. Akhiri dengan ringkasan hasil, daftar file yang dibuat/diubah, pemeriksaan yang benar-benar dilakukan, risiko, dan keputusan berikutnya. Jelaskan jenis hasil sesuai tahap yang diizinkan; implementasi lokal bukan kesiapan produksi. Bila ada perubahan arsitektur/dokumen fondasi, sertakan ZIP terverifikasi sesuai aturan pengemasan di atas.
